# Spolysis v2: options for discussion

Status: proposals only; no option, delivery date, price, or priority is approved.
The recommendations below are suggestions for the owner to accept, change, or reject.
Creating this document does not authorize implementation or deployment of these improvements.

## Starting point

The MVP accepts a chosen stroke and handedness, selects the strongest swing, reconstructs relative motion, compares it with reference motion, and returns an overlay and interactive 3D playback.
Image observations remain internal inputs required by the existing reconstruction and projection pipeline.
Coaching text is deterministic and based on measured differences.
The recorded validation and external release requirements are in [Implementation status](docs/IMPLEMENTATION_STATUS.md).
Those existing release requirements should be verified separately from choosing new features.

## 1. Reconstruction quality and evidence

Current limitation: the model is pretrained and there is no recorded quantitative benchmark on held-out tennis players and camera conditions.
Successful video processing does not establish joint-angle accuracy.

| Option | Why consider it? | Tradeoff |
|---|---|---|
| A. Benchmark the current pipeline first | Establishes errors by stroke, camera position, handedness, and visibility before changing models | Requires trustworthy reference measurements and representative recordings |
| B. Fine-tune the existing model on approved tennis data | Could reduce errors specific to fast tennis motion while keeping the current interfaces | Needs suitable training rights, subject-separated evaluation, and evidence of improvement |
| C. Evaluate a different reconstruction approach | Could address limitations that fine-tuning cannot solve | Requires a model comparison and potentially different coordinates, projection, and deployment contracts |

Recommendation: A first; choose B or C only after identifying the dominant errors.
The [MotionBERT repository](https://github.com/Walter0807/MotionBERT) documents its reconstruction model and training approach; suitability for this app must still be evaluated on tennis recordings.
If selected, define acceptable angle error, temporal stability, rejection rate, and latency before comparing candidates.
Decision needed: which evaluation data can we obtain, and what quality threshold should a released correction meet?

## 2. Confidence and when to withhold feedback

Current limitation: the app displays pose visibility, which is not the same as certainty in the reconstructed angles or suggested correction.

| Option | Why consider it? | Tradeoff |
|---|---|---|
| A. Add clearer recording guidance and targeted rejection reasons | Helps users fix unsuitable framing or lighting before retrying | Does not quantify uncertainty in otherwise accepted recordings |
| B. Suppress corrections for joints or phases with insufficient evidence | Reduces unsupported feedback while retaining useful parts of a recording | Requires calibrated thresholds and a clear partial-result experience |
| C. Require an additional capture angle for selected cases | Could provide more evidence where one view is ambiguous | Adds capture friction and requires new reconstruction and alignment work |

Recommendation: evaluate A and B together after establishing the quality benchmark.
Keep C as an alternative if single-view error remains unacceptable in important cases.
If selected, test whether uncertain cases are withheld without rejecting most usable recordings.
Decision needed: should an uncertain result show partial feedback, playback only, or require a new recording?

## 3. Swing selection and longer practice sessions

Current limitation: the strongest wrist-motion window may not be the swing the player intended to review.

| Option | Why consider it? | Tradeoff |
|---|---|---|
| A. Let the player choose or trim a swing before analysis | Gives explicit control and can reduce unnecessary processing | Adds an interaction before upload or analysis |
| B. Detect candidate swings and let the player choose one | Reduces manual trimming while preserving user control | Candidate detection must distinguish swings from walking and preparation |
| C. Analyze every swing and produce a session summary | Supports consistency review across a practice session | Changes the result model, progress UI, processing volume, and comparison semantics |

Recommendation: A as a focused next option; compare B if trimming proves cumbersome.
Choose C only if session-level review is a product priority.
If selected, validate that players can reliably choose the intended swing and understand which frames were analyzed.
Decision needed: is the next release focused on one excellent correction or whole-session review?

## 4. Reference motion and personalization

Current limitation: selecting a reference by broad stroke category can mix legitimate differences in stance, style, and player technique.
A difference from one reference is not automatically a technical fault.

| Option | Why consider it? | Tradeoff |
|---|---|---|
| A. Expand reference metadata and match compatible styles | Makes comparisons easier to explain and reduces mismatched examples | Requires reliable annotations and a sufficiently varied reference library |
| B. Compare with the player's own earlier or coach-approved swing | Supports personal progress without requiring exact imitation of another athlete | Requires baseline selection, consent, and consistent capture conditions |
| C. Add a coach-reviewed reference and feedback workflow | Adds expert context to corrections | Introduces review operations, permissions, turnaround time, and additional product roles |

Recommendation: A for reference quality; consider B if progress tracking is central to the product.
C is a distinct service direction that should be chosen explicitly.
If selected, verify reference compatibility and preserve dataset attribution in derived artifacts.
Decision needed: should the comparison target be a matched reference, the player's baseline, or a coach-selected target?

## 5. Results, learning, and progress

Current limitation: playback and analysis history are available, but the app does not yet establish whether a suggested change helps the player over time.

| Option | Why consider it? | Tradeoff |
|---|---|---|
| A. Synchronize video and 3D playback around the relevant phase | Makes the existing result easier to understand | Requires reliable timestamps and responsive playback on real devices |
| B. Show trends across comparable recordings | Makes repeated practice easier to review | Trends can mislead when camera angle, model version, or reference changes |
| C. Add a structured practice plan and follow-up recording | Connects observation with an action and a later check | Requires reviewed coaching content and careful success criteria |

Recommendation: A first if usability sessions show that people struggle to interpret results.
Choose B or C based on whether players want measurement history or practice guidance.
If selected, validate comprehension with players and avoid interpreting model-version changes as player improvement.
Decision needed: should the next experience emphasize understanding one result or following a practice program?

## 6. Reliability, latency, and processing cost

Current limitation: Temporal invokes one GPU activity, and completed results are cached by job ID.
A failure before completion can repeat earlier work.

| Option | Why consider it? | Tradeoff |
|---|---|---|
| A. Measure stage timings, failures, retries, and delivered-result cost | Identifies actual bottlenecks while keeping the current execution shape | Visibility alone does not change retry cost or latency |
| B. Persist selected stage outputs and resume from checkpoints | Can avoid repeating expensive successful stages | Requires artifact versioning, cleanup, and retry-safe stage contracts |
| C. Split the GPU activity into independently retried workflow stages | Gives explicit stage progress and recovery boundaries | Adds orchestration transitions, transfer overhead, and possible model reloads |

Recommendation: A first, then B if repeated expensive work is material.
C is a structural alternative when separate execution and recovery boundaries justify it.
[Temporal's activity documentation](https://docs.temporal.io/activities) explains activity boundaries and the need for idempotent retries.
If selected, compare end-to-end latency and cost under injected failures, not just successful processing time.
Decision needed: is the main target faster results, cheaper retries, more detailed progress, or a combination?

## 7. Storage retention and user control

Current limitation: uploads and analysis artifacts accumulate, and a future retention policy has not been selected here.

| Option | Why consider it? | Tradeoff |
|---|---|---|
| A. Retain history until the user deletes it | Supports long-term review and personal comparisons | Requires dependable deletion across storage, database, and in-flight jobs; storage grows |
| B. Expire raw uploads and intermediate artifacts while retaining final results | Reduces retained data while preserving a usable history | Limits later reprocessing and requires clear explanation of what is kept |
| C. Offer user-selected retention with a defined default | Gives players control over convenience and retained footage | Adds settings and more lifecycle cases to verify |

Recommendation: discuss B with explicit user deletion as the initial policy candidate.
No retention duration is selected or configured by this cleanup.
[R2 lifecycle rules](https://developers.cloudflare.com/r2/buckets/object-lifecycles/) can expire objects, but application records, retry windows, and user-visible availability must be coordinated separately.
If selected, verify deletion and expiry across all artifacts and ensure retries cannot recreate deleted results.
Decision needed: what should be retained, for how long, and what should a user be able to recover?

## 8. Pricing and access

Current limitation: billing is not enabled in the current flow.
The legacy database label does not represent an enforced paid entitlement.

| Option | Why consider it? | Tradeoff |
|---|---|---|
| A. Keep an invitation-only evaluation period | Provides usage and quality evidence before choosing a commercial offer | Requires explicit usage limits and a compute budget |
| B. Sell analysis credits | Connects payment to an understandable unit of use | Requires purchase verification, a credit ledger, and clear failed-analysis handling |
| C. Offer a subscription with an explicit allowance | Can suit regular practice and predictable access | Needs usage evidence, renewal handling, and server-side entitlement enforcement |

Recommendation: measure delivered-result cost and repeat usage before choosing B or C.
No price, allowance, billing provider, or refund policy is selected in this document.
If selected, validate purchase restoration, duplicate purchase events, exhausted allowances, and failed jobs without double charging.
Decision needed: is the initial audience occasional players, regular trainees, or a controlled evaluation group?

## 9. Remove legacy contract terminology

Current limitation: `tier`, the stored `premium` value, optional historical result fields, and `complete_premium` remain compatibility contracts.
The standalone classifier and its training tooling are removed; historical migration files still describe the schema that created existing records.

| Option | Why consider it? | Tradeoff |
|---|---|---|
| A. Retain compatibility names and document their meaning | Keeps existing clients, stored history, and workflow callbacks readable | Leaves terminology that no longer describes the product |
| B. Introduce an analysis schema version and migrate clients and workers gradually | Gives the single analysis product an accurate contract while preserving history | Requires a forward migration, rollout order, and handling for in-flight workflows |
| C. Cut over to a new contract after stopping old clients and workflows | Removes compatibility code in one coordinated release | Requires a confirmed cutover window and an explicit decision about historical records |

Recommendation: B when the owner chooses to change these interfaces.
This cleanup retains A to avoid silently changing stored data or deployed callbacks.
If selected, test old history, new analyses, callback retries, and mixed client/worker versions during rollout.
Decision needed: must existing builds and analyses continue working throughout the migration?

## Choosing a v2 scope

My suggested first discussion is reconstruction evidence, uncertainty handling, and choosing the intended swing.
These address whether a correction is useful before expanding the number of features or introducing payment.
That ordering is a recommendation, not a scheduled roadmap.

All decisions above remain open.
Record selected option letters, acceptance criteria, and deferred alternatives here after the owner chooses them.
